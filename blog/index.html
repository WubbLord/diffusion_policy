Action-Interface Mismatch in Joint-Space Imitation Learning

Diffusion Policy can learn joint-space desired motion, but those labels are executable only when they match the controller's action interface. A small inverse-controller adapter can repair that mismatch on simple tasks, while contact-heavy tasks expose the limits of local command translation.

Brian Zhang and Sourish Pramanik · Spring 2026

Introduction

Diffusion Policy [1] represents a robot policy as a conditional denoising process over future actions. It predicts high-dimensional, multimodal action sequences in a receding-horizon loop. But an action is not just a vector to imitate. It is a contract with a controller: the same desired motion can mean different things under operational-space, joint-position, velocity, or torque control. In RoboMimic [2], the logged actions are operational-space end-effector commands for a robosuite [3] controller, not raw joint commands.

This project asks what happens when we keep the same demonstrations but change the deployment interface to joint-position control. A tempting joint-space label is available in every low-dimensional RoboMimic [2] trajectory: Δqdemo[t] = q[t+1] - q[t]. That label is a real measured arm transition, and Diffusion Policy [1] can model it. The problem is semantic: a measured state transition is not automatically the command that a different controller should receive.

Main claim: the key failure mode is an action-interface mismatch. Demonstration-derived joint deltas are useful desired transitions, but they are not executable actions until they are mapped into the deployment controller's command interface.

The experiments support this claim. On Can MH, the original end-effector Diffusion Policy [1] reaches 49/50 test successes. A joint-delta Diffusion Policy [1] executed directly through robosuite [3] JOINT_POSITION gets 0/50. The same joint-delta policy, passed through a learned inverse-controller adapter, reaches 50/50. The failure is therefore not simply that a diffusion model cannot predict joint-space motion. The failure is that the policy output and the evaluation controller speak different action languages.

Related Work

Diffusion Policy by Chi et al. [1] formulates visuomotor control as denoising over robot action sequences and reports strong performance across simulated and real manipulation benchmarks, including RoboMimic [2]. We keep the same low-dimensional diffusion policy pipeline and focus on a detail that is easy to overlook: the action vector has to mean something to the controller that executes it. A joint delta computed from the next logged state can be a useful target, but it still has to be translated before a joint-position controller can use it.

RoboMimic by Mandlekar et al. [2] provides the demonstration datasets and benchmark tasks used here, and robosuite [3] provides the simulator and controller abstractions. The logs contain states, state transitions, and OSC actions. Those OSC actions are commands for the original controller; once evaluation moves to joint-position control, the matching command label is missing.

Recent joint-space diffusion methods address related kinematic issues. HDP introduces RK-Diffuser [4], which learns end-effector and joint trajectories with differentiable kinematics. KStar Diffuser [5] adds a URDF-derived graph and kinematic loss, KADP [6] uses 3D points on the robot body, and RobotDiffuse [7] studies diffusion for constrained manipulator planning. Our experiments keep the standard Diffusion Policy [1] backbone and RoboMimic [2] state, then ask whether desired joint motion can be translated into executable joint-position commands.

State-only imitation learning is another close connection. Radosavovic et al. [8] and DePO [9] learn inverse dynamics when demonstrations do not provide the needed actions. Our adapter plays a similar role for a different controller interface: it turns Δq = q[t+1] - q[t] into the command that the joint-position controller should receive.

This work is also related to action-modeling methods such as Implicit Behavioral Cloning [10] and Behavior Transformer [11], which handle multimodal continuous actions. In our setting, even a good policy class needs labels that the evaluation controller can actually run.

Methods

We modified the RoboMimic [2] low-dimensional Diffusion Policy [1] pipeline as little as possible. The joint-delta policy uses the same UNet diffusion workspace, horizon 16, observation history 2, action execution horizon 8, and 100 DDPM inference steps. The observation includes object state, end-effector pose, gripper proprioception, and joint position. The action is the arm joint transition plus the original gripper command.

The key addition is an adapter f(s, Δqdesired) → u, where u is a physical joint-position command. The adapter is a three-layer MLP with 512 hidden units per layer, SiLU activations, and layer normalization. Its state input is the full low-dimensional simulator state used for adapter training: object, end-effector position and quaternion, gripper qpos, joint position, and joint velocity.

Figure 1. The observed joint transition is treated as a desired motion. The adapter learns to convert that desired motion into a command for the deployment controller.

To train the adapter, we generated synthetic inverse-controller data by probing the simulator around demonstration states. For each RoboMimic [2] timestep, we reset robosuite [3] to the logged simulator state, read the full low-dimensional state st, and compute the observed demo transition Δqdemo = q[t+1] - q[t]. We then sample 32 candidate physical joint-position commands u in radians, clip them to [-0.25, 0.25] per joint, convert them to the normalized controller range by dividing by 0.25, append the logged gripper command, and execute one JOINT_POSITION step.

The command samples are deliberately concentrated near plausible demo motion while still covering off-demo directions. The first anchors are 0, Δqdemo, 2Δqdemo, 4Δqdemo, 8Δqdemo, 16Δqdemo, and -Δqdemo. The remaining samples mix uniform commands over the full range, scaled-demo commands with factors in [0, 20] plus noise, and zero-mean Gaussian commands. After each probe, we measure the actual resulting transition Δqactual. Each training example is therefore (st, Δqactual) → u: the adapter learns which command would have produced a desired local joint transition from that state. For Can MH alone this produced 2,008,192 one-step trials over 62,756 demonstration timesteps. Across tasks, PH adapters use demos 0:150 for training and 150:200 for validation, while MH adapters use 0:250 and 250:300.

Experiments

1. Is naive joint-space execution the problem?

The first diagnostic compares three Can MH policies under the same 50 seeded rollout protocol. The original end-effector policy uses the native OSC action interface. The naive joint-delta policy sends predicted joint deltas directly to JOINT_POSITION. The adapter policy uses the same joint-delta Diffusion Policy [1] but inserts the learned inverse controller before execution.

Figure 2. Direct joint-delta execution fails, while the adapter recovers Can performance. The original EEF baseline is included as the clearest available baseline.

The joint-delta policy was not obviously random. In an offline validation check conditioned on ground-truth teleoperated state, its arm joint-delta MAE was 0.006985 rad over 1,308 validation timesteps. The mean absolute target delta was 0.009394 rad. This is not perfect, but it is good enough that a 0/50 rollout result points to the interface mismatch rather than simply an untrained model.

2. Can the adapter replay held-out demonstrations?

Before using a learned policy, we tested the adapter with oracle desired deltas from held-out demonstrations. At each step, the desired motion is computed from the demo, but the adapter state is the live simulator state. This tests whether f can keep the robot near the intended joint trajectory after its own small errors accumulate.

The important lesson is that oracle replay success is not a direct score for adapter quality. The adapter's direct job is local: given the current simulator state and a desired joint transition, produce a command whose next-state delta matches that transition. The replay success column asks a harder question: if we chain those local translations through an entire task, do contacts and object state remain close enough for the original demonstration timing to still work?

Tool Hang and Transport expose why that distinction matters. Tool Hang is a long-horizon, contact-rich precision task: the robot has to grasp the tool with the right orientation, approach the frame, catch the hook, and release without knocking the object out of the intended contact mode. A small joint tracking error can leave the tool visually close but mechanically wrong. Transport is harder for a different reason: it is bimanual, has a 16-dimensional joint command, and requires coordinated object transfer between two arms. Transport PH has a modest replay delta MAE but only 17/50 replay success, which suggests that task-level coordination and contact timing are failing even when local joint tracking is not disastrous. Transport MH fails both locally and globally, with much larger delta error and 0/50 success.

3. Does the full joint-delta policy work beyond Can?

We trained joint-delta Diffusion Policies [1] for the available RoboMimic [2] low-dimensional variants, usually for 5000 epochs. The full pipeline combines the learned policy with the held-out-demo adapter. For context, Figure 4 also includes the original Diffusion Policy [1] paper's reported RoboMimic [2] state-policy results for the closest matching architecture, DiffusionPolicy-C.

Figure 4. The full joint-delta DP plus adapter pipeline reaches near-perfect success on Can and Lift, partial success on Square, fails on Tool Hang and Transport PH, and reaches 5/50 on Transport MH. The adjacent paper baseline is the original Diffusion Policy [1] state-policy DiffusionPolicy-C max success rate for the same task variant.

This result gives a more nuanced answer than "joint space works" or "joint space fails." On Can and Lift, desired joint transitions plus an adapter are enough. On Square, they are useful but not at the original Diffusion Policy [1] level. On Tool Hang and Transport, even the adapter and two-arm-compatible runner are not enough for reliable task completion.

We also tested a learned adapter for the original OSC_POSE action interface. This adapter was trained from synthetic probes exactly like the joint-position adapter: reset to demo states, send sampled OSC commands, measure the actual joint delta, and learn (s, Δq) → uOSC. It tracks held-out demo deltas accurately in one step, but fails in full policy rollout.

4. Should the adapter be run as a closed-loop servo?

The final experiment asks whether a desired joint transition should be executed in one shot or iteratively. In closed-loop mode, the runner sets qtarget = qcurrent + Δqdesired. For k inner steps, it recomputes the residual qtarget - qcurrent, sends that residual through the adapter, and steps the simulator. Thus, the first inner step uses the full desired delta and later steps try to remove the remaining error.

Figure 5. Each point is test success over 50 rollouts. Color identifies the task; dotted lines are PH datasets and solid lines are MH datasets.

The closed-loop result is surprising at first: more servo iterations do not generally improve task success. Can MH drops from 50/50 at k=1 to 40/50 at k=2 and 12/50 at k=3. Lift MH is the main exception, with 50/50 at k=2. The reason is that k is not just extra adapter computation. Each inner step is a real robosuite [3] control step, so closed-loop execution changes the amount of simulated time spent on each policy action. Better local joint tracking can damage contact timing.

Discussion

Our central contribution is to make the action-interface mismatch explicit. RoboMimic [2] demonstrations contain both state transitions and controller actions, but those objects are not interchangeable. A measured joint transition tells us where the arm went; it does not tell us which command a different controller should receive to reproduce that motion. The Can MH diagnostic isolates this point sharply: the original end-effector policy succeeds, the naive joint-delta policy gets 0/50, and the same joint-delta policy recovers to 50/50 once its desired motion is translated through an inverse-controller adapter.

The second contribution is the adapter formulation itself. We treat Δq = q[t+1] - q[t] as a desired local transition, not as an action. The learned adapter maps (s, Δqdesired) into the command space of the deployment controller. This lets us keep the trajectory-modeling strengths of Diffusion Policy [1] while adding the missing controller semantics as a separate, testable module. The adapter is small, but it encodes an important prior: actions should be learned in the units and normalization used by the controller that will execute them.

The third contribution is diagnostic. We evaluate the adapter in oracle replay before using a learned policy, which separates policy error from controller-translation error. When oracle replay succeeds but full rollout fails, the policy is the likely bottleneck. When oracle replay fails, the desired transition is not being converted into a robust command sequence. This distinction matters because one-step delta MAE alone can look good while contact-rich rollouts still drift off the demonstration manifold.

The broader empirical contribution is a map of where this idea works. On Can and Lift, the adapter recovers high success and shows that joint-space desired motion is a viable representation for Diffusion Policy [1]. On Square, Tool Hang, and Transport, success drops when contact precision or multi-arm coordination dominates the task. The closed-loop sweep adds another negative result: repeatedly servoing the same desired delta does not reliably help, because each inner step also changes the timing of contact. Better local tracking is not automatically better task execution. The probe-trained OSC adapter sharpens the same point: even excellent one-step delta tracking does not guarantee a usable rollout adapter when the inverse action interface is branch-ambiguous.

These results also define the limits of the current system. All experiments are in simulation, and the adapter assumes accurate low-dimensional state. Synthetic inverse-controller data is expensive: Can MH alone used over two million one-step probes. Command saturation is common, so some requested deltas exceed what the controller can realize in one step. Finally, the adapter is local. It can translate a desired joint transition, but it does not reason about object pose, future contacts, or two-arm coordination beyond what is already present in the policy output.

Conclusion

The main result is that joint-space imitation can fail for an interface reason, not just a modeling reason. Diffusion Policy [1] can learn useful joint-space desired transitions, and on Can and Lift those transitions can drive high-success policies once translated into the right command space. Without that translation, observed joint deltas are not controller commands.

The broader lesson is that action representation is not only a question of dimensionality or policy architecture. It is a question of interface semantics. A state transition, an end-effector command, a normalized joint-position command, and a torque are different objects, even when they all move the same robot. For imitation learning systems that reuse offline demonstrations under new controllers, modeling the adapter between these interfaces can be as important as modeling the policy.
